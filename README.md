# Мониторинг реализации государственных программ

Учебный аналитический модуль для двух программ: жилищной и научной. В комплекте сохранены 6 792 наблюдения из шести исходных SDMX/XML, оригинальные материалы и история импорта. Интерфейс на русском языке: загрузка с предпросмотром, фильтры, таблица, шесть видов визуализации, CSV и API чтения.

Основное контейнерное развёртывание: Django 5.2, Gunicorn, WhiteNoise и PostgreSQL 17. Для простого запуска на Windows сохранён вариант с SQLite и Python 3.12–3.14. Числа хранятся точно: PostgreSQL `numeric`, SQLite — десятичный текст с API Decimal. Bootstrap и Chart.js поставляются локально, CDN не нужен.

Полный код доработок находится в ветке [feature/postgres-okfs-analytics](https://github.com/Hawkeye228666/state-program-monitoring/tree/feature/postgres-okfs-analytics). В основную ветку изменения автоматически не сливаются.

## Быстрый запуск на Windows с SQLite

Распакуйте проект в отдельную папку. Рядом с `run_windows.bat` должны находиться `manage.py`, `requirements.txt`, `db.sqlite3`, `config/` и `monitor/`. Установите обычный 64-разрядный Python 3.12, 3.13 или 3.14 с pip и venv, затем запустите **run_windows.bat** двойным щелчком.

Скрипт найдёт Python, создаст `.venv`, установит зависимости, выполнит миграции, подготовит роли и статику. Если нет активной учётной записи с паролем и правом просмотра, он предложит создать первого администратора: введите логин и свой пароль. Символы пароля при вводе не отображаются. **Готового логина и пароля в проекте нет.**

После запуска откройте [http://127.0.0.1:8000/](http://127.0.0.1:8000/) и войдите под своей учётной записью. Пока работает сайт, оставьте окно открытым. Остановка: Ctrl+C. BAT запускает локальный SQLite-вариант на loopback; контейнерное развёртывание описано ниже.

То же вручную в PowerShell из папки проекта:

```powershell
py -3.14 -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r requirements.txt
.\.venv\Scripts\python.exe manage.py bootstrap_local
.\.venv\Scripts\python.exe manage.py runserver 127.0.0.1:8000
```

Замените `-3.14` на свою версию Python. Если `py` не зарегистрирован, используйте полный путь к установленному `python.exe`; BAT умеет искать стандартные места установки. Активация окружения и изменение ExecutionPolicy не нужны. Интернет требуется для первой установки зависимостей.

`bootstrap_local` выполняет `migrate`, `seed_programs`, `setup_roles`, `collectstatic` и при необходимости интерактивное создание первой учётной записи. Для повторной настройки без запроса пользователя: `manage.py bootstrap_local --no-admin`. Для создания ещё одного администратора: `manage.py createsuperuser`.

Данные уже находятся в `db.sqlite3`. Не удаляйте и не заменяйте этот файл: пользовательские правки и история хранятся именно в нём. Повторный импорт исходного архива не создаёт дубликатов, но не заменяет резервное копирование.

## Контейнеры и PostgreSQL

Нужны Docker Engine или Docker Desktop с Docker Compose v2 и Python 3.12–3.14 для служебных скриптов. В примерах `python` означает ваш установленный Python; на Windows можно использовать `py -3.14` или `.\.venv\Scripts\python.exe`.

Перед первым запуском создайте локальный файл окружения:

```powershell
python scripts/create_env.py
docker compose config --quiet
docker compose up --build -d --wait app
```

Скрипт создаёт `.env` с тремя разными случайными секретами и не показывает их. Существующий `.env` не перезаписывается. `.env.example` содержит только имена и безопасные примеры настроек. Не публикуйте `.env` и резервные копии с учётными записями. Секреты и SQLite не включаются в образ.

Compose поднимает PostgreSQL, ждёт готовности БД, запускает отдельный одноразовый сервис миграций и затем Gunicorn. WhiteNoise выдаёт собранную статику. Приложение работает от UID 10001, пишет журналы в стандартные потоки и имеет `/healthz/`. Порт БД наружу не публикуется. HTTP по умолчанию доступен только на `127.0.0.1:8000`. PostgreSQL, загруженные файлы и резервные копии имеют отдельные именованные тома.

### Первый перенос существующей SQLite-базы

После первого `up` PostgreSQL содержит только схему. **Перенесите существующую базу до создания пользователей, групп и импорта в PostgreSQL.** Если в PostgreSQL уже есть рабочие записи, команда откажется их перезаписывать.

Остановите локальный сервер SQLite и приложение Compose, затем выполните в PowerShell:

```powershell
docker compose stop app
New-Item -ItemType Directory -Path transfer -Force
docker compose run --rm --no-deps -v "${PWD}/db.sqlite3:/legacy/db.sqlite3:ro" -v "${PWD}/data:/legacy/data:ro" -v "${PWD}/transfer:/transfer" app python manage.py transfer_sqlite --source /legacy/db.sqlite3 --media-source /legacy/data --backup-dir /transfer
docker compose run --rm --no-deps app python manage.py setup_roles
docker compose start app
```

Команда сначала делает согласованную резервную копию SQLite в `transfer/`, затем переносит реальные записи всех поддержанных таблиц, исходные XML и историю, сохраняет ID, пользовательские метаданные и существующие учётные записи. Она сверяет полные контрольные суммы строк, внешние ключи и последовательности идентификаторов. JSON-отчёт сохраняется рядом с копией. XML заново для переноса не импортируется.

Если в исходной SQLite не было рабочей учётной записи, создайте её интерактивно:

```powershell
docker compose exec app python manage.py createsuperuser
```

Откройте [http://127.0.0.1:8000/](http://127.0.0.1:8000/) и войдите. После переноса прежние учётные записи сохраняют свои пароли и права. Особенности прав на bind mount в Linux и порядок отката описаны в [инструкции эксплуатации](docs/operations.md).

### Журналы, обновление и остановка

```powershell
docker compose ps
docker compose logs --tail 100 -f app db migrate
python scripts/backup.py --output backups/before-update
docker compose stop app
docker compose build app
docker compose run --rm --no-deps app python manage.py migrate --noinput
docker compose run --rm --no-deps app python manage.py setup_roles
docker compose up -d --no-deps --wait app
docker compose down
```

Перед обновлением получите нужную версию исходного кода. `backups/before-update` должен быть новым каталогом; выберите другое имя для следующей копии. `down` штатно останавливает сервисы и сохраняет именованные тома. Не добавляйте удаление томов к инструкции обновления. База и загруженные XML переживают пересоздание контейнеров.

### Резервная копия и проверка восстановления

```powershell
python scripts/backup.py --output backups/pilot-check
python scripts/restore.py --backup backups/pilot-check --database monitor_restore_check
docker compose exec app python manage.py db_fingerprint --check-files
```

Копирование кратко останавливает приложение, сохраняет `pg_dump`, файлы и их контрольные суммы, затем возвращает приложение в прежнее состояние. Восстановление выполняется **в новую отдельную БД**, сравнивает полные контрольные суммы и не переключает рабочее приложение. Имя тестовой БД должно быть новым. Полный порядок восстановления, переключения и отката — в [docs/operations.md](docs/operations.md).

## Вход, роли и работа с данными

В Django Admin по адресу `/admin/` администратор создаёт пользователей и назначает группы:

| Роль | Возможности |
| --- | --- |
| Аналитик | Паспорта, таблица, фильтры, графики, CSV и API чтения |
| Оператор загрузки | Чтение и загрузка SDMX/XML/ZIP с предпросмотром и подтверждением |
| Администратор | Управление данными и пользователями; для `/admin/` также нужен `is_staff` |

Неавторизованный посетитель получает форму входа. Пользователь без нужного права получает отказ. Самостоятельной публичной регистрации нет. Корпоративная авторизация не заявлена.

1. Откройте паспорт одной из двух программ и раздел «Данные и графики».
2. Выберите режим одного показателя или всех показателей программы, территории, периоды, уровень и дополнительные измерения. Для ОКФС доступны фактические категории и состояния, а не искусственные нули.
3. Нажмите «Применить фильтры». Таблица показывает по 50 строк; CSV и графики используют всю выборку. Фильтры можно сохранить в сессии.
4. Для dumbbell задайте два периода одного показателя; разница процентов подписывается в п.п. Для scatter включите два показателя через режим всей программы и выберите X/Y. Для boxplot выберите один показатель и один период. Выбирайте один уровень территории и одну сопоставимую комбинацию измерений. Линейный, столбчатый графики и тепловая карта также сохранены.
5. Посмотрите причины исключения регионов с пропусками, затем скачайте PNG или CSV. Нули остаются значениями, пропуски нулями не заменяются.
6. Оператор загружает общий ZIP либо отдельные ZIP/XML/SDMX, проверяет предпросмотр и назначение программы, подтверждает импорт и видит результат в истории. Предпросмотр не меняет наблюдения.

Для 44198 квартал хранится отдельно от года: `2014-Q1`, `2014-Q2`, `2014-Q3`. У территории 643 и ОКФС 200 значения равны 111,7; 120,3; 125. Код 199 не равен 200 и в исходных наблюдениях не используется. Нельзя складывать итог с отдельными формами собственности или усреднять проценты без методики и весов.

API приложения: `/api/v1/indicators/` и `/api/v1/observations/`, доступные по сессии авторизованного читателя. Есть фильтры, пагинация и метаданные источника. Это API учебного модуля, не внешний API ЕМИСС. Контракт, ошибки и примеры CSV описаны в [docs/api.md](docs/api.md).

## Проверки

В локальном окружении:

```powershell
.\run_windows.bat --check
```

Эта команда готовит роли и статику, выполняет Django check, проверку миграций и тесты, не создавая пользователя. Для запуска отдельных проверок:

```powershell
.\.venv\Scripts\python.exe manage.py check
.\.venv\Scripts\python.exe manage.py makemigrations --check --dry-run
.\.venv\Scripts\python.exe manage.py test monitor --verbosity 2
.\.venv\Scripts\python.exe manage.py audit_okfs --output docs/okfs-audit.json
```

Для тестов PostgreSQL используйте CI или отдельную тестовую БД с разрешением создавать тестовые базы. Учётная запись рабочего приложения не является суперпользователем и не получает такие права по умолчанию. Workflow `.github/workflows/checks.yml` проверяет PostgreSQL и контейнерный сценарий. Фактически выполненные проверки и ограничения среды фиксируются в отчёте о проверках; наличие workflow само по себе не означает успешного прохождения.

На текущем компьютере Docker CLI/daemon недоступны. Локальную сборку и запуск Compose, работу контейнеров и сохранность томов после их пересоздания нельзя считать проверенными только на основании серверных тестов. Результаты доступных проверок PostgreSQL и CI указаны отдельно в итоговом отчёте.

## Материалы и ограничения

- [Исходное состояние](docs/baseline.md), [аудит ОКФС](docs/okfs-audit.md), [описание визуализаций](docs/visualizations.md).
- [Эксплуатация, перенос, резервирование и откат](docs/operations.md), [API и CSV](docs/api.md).
- [Предложение пилота для организации типа Мосстата](docs/integration-mosstat.md). Внедрение в организацию не проводилось; её внутренние системы и API не предполагаются известными.
- `materials/` содержит неизменённые исходные DOCX/ZIP, `data/sources/` — точные исходные XML с именами по SHA-256.
- `deliverables/` содержит итоговые материалы для защиты: презентацию PPTX, текст выступления и отчёты.

Поддержан предоставленный вариант GenericData SDMX 1.0, а не произвольные структуры SDMX. Доступны опубликованные фактические значения; подтверждённые планы и расчёт процента выполнения программы отсутствуют. Историческая классификация территорий относится к исходному набору. Между показателями нельзя автоматически сопоставлять несогласованные измерения и периоды.

Пилот рассчитан на опубликованные агрегированные данные и небольшой набор наблюдений. Для промышленного размещения согласуются HTTPS на организационном ingress, резервирование вне сервера, мониторинг, SSO, сроки хранения и нагрузка. Локальный `runserver` предназначен для демонстрации. Данные пользователей и пароли не должны попадать в Git, архивы для защиты и публичные журналы.
