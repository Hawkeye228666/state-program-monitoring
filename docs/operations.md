# Развёртывание и сохранность данных

## Архитектура и версии

Compose содержит PostgreSQL `postgres:17.11-trixie`, однократный сервис миграций и приложение на Gunicorn. Python закреплён как `python:3.12.15-slim-trixie`. Приложение работает под UID/GID 10001 с файловой системой только для чтения, томом источников `/app/data` и временным каталогом. Gunicorn пишет access/error logs в стандартные потоки. WhiteNoise выдаёт локальную статику, подготовленную collectstatic при сборке. Reverse proxy для локального пилота не требуется. TLS и доверенный ingress организации согласуются отдельно.

Теги проверены по [официальному образу Python](https://hub.docker.com/_/python) и [официальному образу PostgreSQL](https://hub.docker.com/_/postgres). Для PostgreSQL 17 именованный том монтируется в `/var/lib/postgresql/data`. Изменение пути PGDATA в PostgreSQL 18 к этой версии не применяется. Обновление major-версии требует отдельного переноса данных.

Django обновлён до `5.2.19` из поддерживаемой LTS-ветки 5.2 с [исправлениями безопасности от 3 ноября 2026](https://docs.djangoproject.com/en/5.2/releases/5.2.19/). Зависимости закреплены в requirements.txt. При плановом обновлении повторяются проверки и анализируются актуальные security releases.

## Первоначальный запуск

Нужны Docker Engine/Desktop с Linux-контейнерами и Compose v2. Python на хосте нужен для вспомогательных скриптов.

```text
python scripts/create_env.py
docker compose config --quiet
docker compose up --build -d --wait app
```

Открыть http://127.0.0.1:8000/. База первоначально пустая. Перенос старой SQLite выполняется **до** создания ролей, пользователей и загрузок. Для чистого запуска без старой базы:

```text
docker compose exec app python manage.py setup_roles
docker compose exec app python manage.py createsuperuser
```

Администратор создаёт пользователей и назначает группы через `/admin/`. Паролей по умолчанию нет. `.env.example` содержит пустые значения. `.env` исключён из Git и Docker-контекста. Пароли PostgreSQL и приложения различаются. Приложение подключается к `db` под ролью monitor_app без SUPERUSER, CREATEDB и CREATEROLE. Порт БД на хост не публикуется, веб-порт по умолчанию привязан к 127.0.0.1.

После pg_isready сервис migrate выполняет аутентифицированный SELECT 1 с ограниченным ожиданием и применяет миграции. Запросы обслуживаются после успешной миграции. `/healthz/` проверяет доступ к БД и возвращает 503 при ошибке.

За доверенным TLS-ingress можно включить DJANGO_COOKIE_SECURE=1 и DJANGO_SSL_REDIRECT=1. Флаг DJANGO_TRUST_PROXY_SSL=1 разрешён только когда ingress гарантированно перезаписывает X-Forwarded-Proto и прямой доступ к app закрыт. По умолчанию заголовок не считается доверенным. Health endpoint исключён из перенаправления HTTPS для внутренней проверки контейнера.

## Перенос SQLite

`transfer_sqlite` переносит существующие записи, а не заменяет их повторным XML-импортом. Сохраняются ID, справочники и правки метаданных, наблюдения, источники, история загрузок, сессии, пользователи, password hashes, группы и права, журнал администратора, если эти таблицы присутствуют. История django_migrations целевой PostgreSQL остаётся её собственной. Неизвестные таблицы/колонки вызывают отказ вместо частичного переноса.

1. Остановить запись в исходное приложение и сохранить SQLite вместе с каталогом data/. Оригинальные материалы не менять.
2. Применить миграции к пустой PostgreSQL командой первоначального запуска и остановить app. Не создавать пользователей, группы или импорты в целевой базе. Разрешены только content types/permissions от миграций.
3. Создать каталог transfer/. На Linux разрешить запись UID 10001 в этот каталог, например `sudo chown 10001:10001 transfer`. В Windows bind mounts обслуживает Docker Desktop.
4. Выполнить из PowerShell в корне проекта:

```powershell
docker compose stop app
New-Item -ItemType Directory -Force transfer
docker compose run --rm --no-deps -v "${PWD}/db.sqlite3:/legacy/db.sqlite3:ro" -v "${PWD}/data:/legacy/data:ro" -v "${PWD}/transfer:/transfer" app python manage.py transfer_sqlite --source /legacy/db.sqlite3 --media-source /legacy/data --backup-dir /transfer
docker compose run --rm --no-deps app python manage.py setup_roles
docker compose start app
```

В Bash заменить `${PWD}` на `$PWD`. Если прежний проект находится в другом каталоге, подставить абсолютные пути старых db.sqlite3 и data/. Источники смонтированы только для чтения.

Команда создаёт согласованную копию через SQLite backup API, проверяет integrity_check и foreign_key_check. Копирование всех таблиц выполняется в одной транзакции PostgreSQL. Сохраняются точность чисел и raw_value. SQLite при USE_TZ хранит UTC без зоны: при переносе явно добавляется UTC, без сдвига времени на Москву. Сравниваются количества и SHA-256 всех полей всех строк в стабильном порядке. Проверяются FK, последовательности сбрасываются к max(id). Недостающие content types/permissions новых auth/admin-моделей дополняются.

Для каждого SourceFile проверяются безопасный относительный путь и SHA-256 файла. Файлы копируются в постоянный том без подмены конфликтующего содержимого. Ошибка откатывает БД. Уже скопированные неизменяемые файлы могут остаться без ссылок. В transfer/ сохраняются transfer-report-*.json и sqlite-before-transfer-*.sqlite3. Исходная SQLite не модифицируется. Повторный запуск на непустой PostgreSQL отклоняется.

Откат переноса: остановить контейнерное приложение и запустить прежнюю версию с сохранёнными SQLite и data/. Если после переключения появились новые записи, сохранить обе БД и согласовать обратный перенос этих записей. Автоматического слияния расходящихся БД нет.

## Точность и уникальность

ExactNumericTextField имеет строковый API, физически NUMERIC без ограничения масштаба в PostgreSQL и TEXT в SQLite. Вычисления используют Decimal. NaN/Infinity запрещены, в PostgreSQL это закреплено CHECK. Миграция 0002 явно приводит прежний TEXT через USING numeric_text::numeric, обратная миграция возвращает TEXT. Через float значения не проходят.

Сохранён UNIQUE по indicator, territory, period и обязательному SHA-256 канонических измерений. Period.code различает год и квартал. Отсутствующее ОКФС является отсутствием ключа в каноническом объекте и не становится NULL в полях UNIQUE, поэтому повторный импорт не создаёт дубликаты из-за семантики SQL NULL. Строковые 199 и 200 различаются. FK и индексы сохранены. Значения вне диапазона PostgreSQL NUMERIC вызывают отказ вместо округления.

## Резервное копирование и восстановление

```text
python scripts/backup.py --output backups/pilot-01
python scripts/restore.py --backup backups/pilot-01 --database monitor_restore_check
```

backup.py останавливает app для согласованного снимка БД и файлов, получает полные fingerprints строк и оригиналов, запускает pg_dump в custom-формате без owner/ACL, копирует архив и data/ на хост, записывает fingerprint.json и backup.json. Если app работал, finally запускает его обратно. Каталог назначения должен быть новым. Бинарный архив не передаётся через stdout PowerShell. Резервирование одной БД без загруженных XML недостаточно.

restore.py создаёт новую изолированную БД с владельцем приложения, запускает pg_restore с exit-on-error, сравнивает все строки и SHA-256 файлов из backup/media. Существующее имя и имя активной БД запрещены. Сохраняется restore-<database>.json. Активные БД и том файлов не меняются. При ошибке тестовая БД остаётся для диагностики. Для повтора выбрать новое имя.

Backup может содержать password hashes и сессии: хранить вне публичного репозитория. Глобальные роли не входят в dump одной БД и восстанавливаются из конфигурации с защищёнными секретами. Планировщик и внешнее защищённое хранилище определяет организация.

Для аварийного переключения на проверенную восстановленную БД: остановить app, сохранить текущее состояние, восстановить media из того же backup в отдельный том, изменить POSTGRES_DB и том sources в Compose override, применить миграции совместимой версии, запустить app и проверить сценарий пользователя. Прежние БД и том оставить до приёмки. Скрипт не перезаписывает активное хранилище автоматически.

## Обновление, журналы и остановка

```text
python scripts/backup.py --output backups/before-update-01
docker compose stop app
docker compose build
docker compose run --rm migrate
docker compose up -d --wait app
docker compose logs -f app db migrate
docker compose stop
```

Перед обновлением сохранить commit и тег прежнего образа. После обновления проверить health, вход и контрольные выборки. Обратная миграция допускается после оценки конкретного изменения схемы. Для изменений с потерей данных восстановить согласованный снимок на прежней версии приложения. Штатные команды не удаляют именованные тома.

## Выполненные и невыполненные проверки

pg-verification.json и pg-verification.log фиксируют нативный PostgreSQL 17.11: миграции, перенос существующих 6792 наблюдений, полные fingerprints, pg_dump/pg_restore в отдельную БД, последовательности, сохранность после перезапуска PostgreSQL, свежий импорт шести XML и повтор, тесты. Интеграционный тест дополнительно переносит копию SQLite с тестовым пользователем, password hash, группой и правами, пользовательской правкой метаданных и историческим импортом с actor, проверяет неизменность UTC-времени.

Docker CLI/Engine на этом Windows-хосте отсутствуют. Локально не проверены сборка образа, запуск Compose, healthchecks контейнеров, выдача статики через Gunicorn и сохранность после пересоздания контейнеров. Перезапуск нативного PostgreSQL не считается этой проверкой. В CI предусмотрены PostgreSQL service и Compose: сборка, health, перенос, backup/restore и fingerprints до/после force-recreate. Наличие YAML не означает успешный запуск CI.
